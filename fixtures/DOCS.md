
# Bozor — документация проекта

Маркетплейс, объединяющий множество отдельных физических магазинов. Бизнес-проект (не учебный).

Репозиторий: https://github.com/yunusrf275-commits/bozor.git

---

## Стек

- Python 3.12
- Django 6.0.7
- PostgreSQL (база `bozor_bd`)
- Bootstrap 5 (подключён локально, без CDN)
- python-decouple (переменные окружения через `.env`)
- Pillow (работа с изображениями)
- psycopg (драйвер PostgreSQL)

Полный список версий — в `requirements.txt`, обновлять командой:
```bash
pip freeze > requirements.txt
```

## Структура настроек

```
config/settings/
    base.py        — общие настройки
    local.py        — локальная разработка (from .base import *)
    production.py   — прод (пока не настроен)
```

Секреты (`SECRET_KEY`, данные БД) — в `.env` (не в git), читаются через `python-decouple`.

`manage.py` настроен на `config.settings.local` по умолчанию — команды `runserver`/`migrate` работают без флага `--settings`.

## Роли пользователей (задумано)

1. **Главный админ** — управляет регионами, категориями, магазинами; блокирует/разблокирует магазины. Заходит только через стандартную Django admin-панель (`/admin/`), отдельной роли в модели `User` не имеет — определяется через `is_staff`/`is_superuser`.
2. **Владелец магазина** — управляет своим магазином (товары, статистика), создаёт своих админов с разными уровнями доступа (список уровней, не произвольные права), принимает заявки и продаёт через QR-код. Роль `shop_owner`. Регистрируется не сам — его создаёт главный админ после проверки документов, выдаёт логин/пароль.
3. **Покупатель** — может покупать без регистрации (указывает телефон продавцу перед отправкой корзины). Регистрация нужна для комментариев, истории покупок, избранных магазинов. Роль `customer`.

Вход у покупателя и продавца — на разных страницах, но одна модель `User` с полем `role`. Обязательная проверка роли на сервере при входе (не полагаемся на "скрытость" URL).

## Приложение `locations`

Модель `Location` — самоссылающаяся (одна модель на все уровни, без хардкода названий):

```python
class Location(models.Model):
    name = CharField
    parent = FK('self', null=True, blank=True, related_name='children')
    level = PositiveSmallIntegerField()  # 1=viloyat, 2=tuman, 3=село (опционально)
    slug = SlugField(unique=True, auto-generate из name)
```

Защита от неправильной вложенности — метод `clean()`: level 1 не может иметь родителя; level > 1 обязан иметь родителя уровня `level - 1` (проверка "бабушка → мама → внучка").

Магазин привязывается либо к туману (level 2, если это районный центр без своего села), либо к селу (level 3, если известно конкретное село) — оба варианта равнозначны для модели `Shop`.

**Management-команды:**
- `load_locations` — грузит `fixtures/viloyat_tuman.json` (14 областей + 199 туманов Узбекистана)
- `add_test_villages` — тестовые данные: по одному селу на каждый туман (имя вида `<туман>1`)

**Admin:** поиск по названию (`search_fields`), фильтр по уровню, `autocomplete_fields` — специально вместо каскадных select'ов (признано избыточным для редких ручных добавлений главным админом).

**AJAX-эндпоинт:** `GET /locations/get-children/?parent_id=<id>` → JSON со списком дочерних locations. Используется в модалке выбора региона в навбаре.

## Приложение `shops`

Модель `Shop`:

```python
class Shop(models.Model):
    name = CharField
    slug = SlugField(unique=True, auto-generate)
    location = FK(Location, PROTECT)
    owner = FK(settings.AUTH_USER_MODEL, PROTECT, null=True, blank=True)
    logo = ImageField(upload_to='shops/logos/%Y/%m/', blank=True)
    is_active = BooleanField(default=True)  # единственный переключатель вкл/выкл
```

Решения:
- **Нет отдельного поля `category`** — магазин продаёт разное, категории определяются через категории его товаров (когда появится `products`), не хардкодятся на самом магазине.
- **Нет поля `status`** (проверка документов) — убрано как избыточное: проверка документов происходит офлайн до создания магазина в системе, поэтому в БД магазин уже создаётся "одобренным". Включение/выключение — только через `is_active`.
- `owner` — `null=True, blank=True` пока не подключена реальная привязка продавца к своему магазину при создании (следующий шаг).

**Management-команда:** `create_test_shops` — по одному тестовому магазину на каждую locations уровня 2 и 3 (название `Do'kon <название локации>`).

## Приложение `accounts`

Кастомная модель пользователя (обязательно настраивается в самом начале проекта, до первых миграций — иначе потребуется полный сброс БД):

```python
class User(AbstractUser):
    role = CharField(choices=[('customer', 'Покупатель'), ('shop_owner', 'Владелец магазина')], default='customer')
    phone = CharField(blank=True)
```

`AUTH_USER_MODEL = 'accounts.User'` в `config/settings/base.py`.

**Вход продавца:** `/accounts/seller/login/` — проверяет `role == 'shop_owner' and not is_staff`.
**Вход/регистрация покупателя:** `/accounts/login/`, `/accounts/register/` — проверяет `role == 'customer' and not is_staff`.
**Выход:** `/accounts/logout/`.

Пароли — только через `User.objects.create_user()` (хэширует автоматически). Одинаковый текст ошибки для "неверный пароль" и "неверная роль", чтобы не раскрывать существование аккаунта с другой ролью.

Суперпользователь (`is_staff`) исключён из обоих пользовательских входов — заходит только через `/admin/`.

## Приложение `pages`

- `home` (`/`) — главная страница.
- Список магазинов: фильтр по `is_active=True`, опционально по выбранному региону.
- **Рандом + пагинация по 20** — список id перемешивается один раз и сохраняется в сессию (ключ `shops_order_<location_id>`), чтобы при подгрузке следующих страниц магазины не терялись/не дублировались. При смене фильтра — новый ключ сессии, новый рандом.
- **Бесконечная прокрутка** — AJAX через `?ajax=1&page=N&location=X`, IntersectionObserver в `static/js/main.js` подгружает `pages/_shop_cards.html` (партиал с карточками) при достижении низа страницы.
- Функция `get_descendant_ids(location)` — собирает id локации + все её дочерние + внучатые, чтобы фильтр по региону учитывал магазины, привязанные на любом вложенном уровне.

**Навбар** (`templates/includes/navbar.html`):
- Кнопка "Регион" → модалка с пошаговым выбором (все области → клик → её районы, с полем поиска на обоих экранах). Список областей рендерится через context processor `locations.context_processors.regions`.
- Кнопка "Войти"/имя пользователя + "Выйти" (для покупателя).

**Футер** — планируется страница "О нас" и другие информационные страницы внутри `pages` (ещё не наполнены).

Маркетплейс, объединяющий множество отдельных физических магазинов + раздел личных объявлений. Бизнес-проект (не учебный).

Репозиторий: https://github.com/yunusrf275-commits/bozor.git

---

## Стек

- Python 3.12, Django 6.0.7
- PostgreSQL (база `bozor_bd`)
- Bootstrap 5 (подключён локально, без CDN)
- python-decouple (`.env`), Pillow, qrcode[pil]

Обновлять `requirements.txt`: `pip freeze > requirements.txt`

## Структура настроек

```
config/settings/base.py / local.py / production.py
```
Секреты — в `.env` (вне git). `manage.py` по умолчанию использует `config.settings.local`.

---

## Роли пользователей

1. **Главный админ** — управляет регионами, категориями, магазинами, объявлениями (модерация); заходит только через `/admin/`, определяется через `is_staff`/`is_superuser`, отдельной роли в `User` не имеет.
2. **Владелец магазина** (`role='shop_owner'`) — управляет своим магазином (товары, статистика, сотрудники, настройки оплаты), может владеть несколькими магазинами. Регистрируется не сам — создаётся главным админом после проверки документов (заявки принимаются на `/accounts/seller/`).
3. **Сотрудник магазина** — тоже `role='shop_owner'` в `User` (входит через тот же вход продавца), но права внутри конкретного магазина определяются через `ShopStaff` (роль: управляющий/менеджер товаров/продавец приёма заказов/наблюдатель). Создаётся **только владельцем магазина** через свой кабинет.
4. **Покупатель** (`role='customer'`) — может покупать без регистрации (указывает телефон при оформлении заказа). Регистрация нужна для истории заказов, избранного, отзывов, личных объявлений.

Вход у покупателя, продавца и админа — на разных URL, одна модель `accounts.User` с полем `role`. Обязательная серверная проверка роли при входе (не полагаемся на скрытость URL); суперпользователи исключены из пользовательских форм входа.

## Приложения и ключевые решения

### `locations`
Самоссылающаяся модель `Location` (viloyat → tuman → село, `level` 1-3, без хардкода названий), с защитой от неправильной вложенности (`clean()`). Магазин/объявление может быть привязано к любому уровню. AJAX: `GET /locations/get-children/?parent_id=<id>`.
Данные: `load_locations` (14 областей, 199 районов из `fixtures/viloyat_tuman.json`), `add_test_villages` (тестовые сёла).

### `categories`
Та же схема, что и `locations` (самоссылающаяся, без ограничения уровней). `load_categories` грузит `fixtures/categories.json` (11 крупных категорий с подкатегориями). AJAX: `/categories/get-children/`.

### `shops`
`Shop`: name, location, owner, logo, is_active (единственный переключатель — нет отдельного поля category у магазина, нет поля status проверки), card_number/card_holder_name (для оплаты по QR, вводит сам владелец через кабинет).
`ShopStaff`: shop, user, role — права проверяются и на сервере (в каждой view), и скрытием кнопок в шаблоне.

### `products`
`Product`: shop, category, price (Decimal), discount_percent (0-100, может быть пустым), stock_quantity, несколько фото через `ProductImage`. `final_price` — вычисляемое свойство. `average_rating`/`reviews_count` — то же для рейтинга.

### `cart` / `orders`
Корзина — в сессии (`cart/cart.py`, класс `Cart`), без модели в БД. Оформление заказа (`checkout`) разбивает корзину по магазинам — один `Order` на магазин, с `OrderItem.price_at_order` (цена фиксируется на момент покупки). Post/Redirect/Get на страницу успеха (защита от дублирования при обновлении страницы). `Order.customer` — необязательное поле, заполняется если покупатель вошёл; гостевые заказы тоже работают. Способ получения (`delivery_method`: pickup/delivery) и адрес — в модели `Order`.

### QR-оплата
`orders:order_qr` генерирует PNG с текстом (карта + сумма + номер заказа) через библиотеку `qrcode`. Не интеграция с банком/Click — просто текстовый QR для ручного перевода, показывается на странице успеха заказа.

### `favorites`
`FavoriteShop`/`FavoriteProduct` — только для зарегистрированных, toggle-логика (add/remove одной кнопкой), `unique_together`.

### `reviews`
`ShopReview`/`ProductReview` — рейтинг 1-5 + текст, **обязательная проверка покупки** перед показом формы (через `OrderItem`), `unique_together` (один отзыв на пользователя, `update_or_create` при повторной отправке).

### `notifications`
Универсальная модель `Notification` (user, text, link, is_read). Создаётся продавцу при новом заказе (всем сотрудникам магазина + владельцу), покупателю — при смене статуса заказа (если `order.customer` заполнен). Счётчик непрочитанных — через context processor, значок 🔔 в навбаре.

### `listings` (личные объявления, как на Avito/OLX)
`Listing`: user, title, category, location, price, phone, status (pending/approved/rejected — **ручная модерация** через админку), несколько фото через `ListingImage`. Подать объявление может только `role='customer'` (продавцы — нет, если хотят подать объявление, заводят отдельный аккаунт покупателя). Фильтр по региону и категории — как на главной. Бесконечная прокрутка (без рандома, сортировка по дате). Автоматизированную ИИ-модерацию решили отложить — старт с ручной проверки главным админом.

### `pages`
`home` — главная (переключатель "Магазины"/"Товары", общие фильтры регион+категория+поиск, рандом+пагинация с фиксацией порядка в сессии — ключ учитывает все фильтры сразу, бесконечная прокрутка через AJAX).
`Page` — модель для информационных страниц (О нас, Условия и т.д.), редактируется **только через админку**, не хардкод в шаблонах. `show_in_footer`/`order` управляют выводом в футере.
`accounts:seller_landing` (`/accounts/seller/`) — публичная страница "Для продавцов" с презентацией + формой заявки (`SellerApplication`: имя, телефон) + кнопкой входа для существующих продавцов.

### Кабинет продавца (`shops` views)
Вкладочная структура (`shops/dashboard_base.html` + `{% block dashboard_content %}`): **Обзор** (статистика: товары, заказы за 30 дней, выручка по завершённым заказам, средний чек, топ-5 товаров, последние заказы), **Товары**, **Заказы**, **Сотрудники** (только владелец), **Настройки** (реквизиты карты, только владелец).

### Кабинет покупателя (`accounts/account_base.html`)
Единый раздел с вкладками: **Мои заказы**, **Избранное**, **Мои объявления** — общая навигация (`.dashboard-nav`, тот же стиль, что у продавца). В навбаре — клик по имени пользователя ведёт в кабинет (отдельные ссылки "Мои заказы"/"Избранное" из навбара убраны).

## Навбар и общий UX

- Регион/Категории — модалки с поиском, AJAX-подгрузкой детей, работают **на текущей странице** (используют `window.location.pathname` + сохраняют остальные GET-параметры), а не жёстко ведут на главную.
- Бесконечная прокрутка — переиспользуемая функция `setupInfiniteScroll(containerId, triggerId)` в `main.js`, вызывается для любой страницы со списком карточек (сейчас: главная и объявления).
- Футер (`includes/footer.html`) показывается **на всех страницах кроме главной** (через переопределение Django template block `{% block footer %}{% endblock %}` в `home.html`) — на главной он бесполезен из-за бесконечной прокрутки.
- Дизайн: единая палитра через CSS-переменные в `static/css/style.css` (изумрудно-зелёный `--bozor-primary` + оранжевый акцент `--bozor-accent`), карточки с мягкой тенью и hover-подъёмом, 2 карточки в ряд на мобильных экранах.
